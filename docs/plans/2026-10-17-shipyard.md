# Shipyard Implementation Plan

> Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Claude Code plugin, `shipyard`, whose `/shipyard <request>` command runs a crew of agents. The crew asks the owner at every unclear point, gets visual approval before any code, builds, tests and reviews, and finishes on a pushed branch.

**Architecture:** One orchestrator skill (`skills/shipyard/SKILL.md`) runs in the main session, because subagents cannot start subagents. It holds every question to the owner and every approval. Five subagents in `agents/` do the work. Run state lives in the target repo (`state.md`, `tasks.md`), so any device can resume a run. The repo is its own marketplace.

**Tech Stack:** Claude Code plugin format (Markdown skills and agents, JSON manifests), Bash for checks and the bootstrap script, `claude plugin validate` / `claude plugin eval`.

**Spec:** `docs/specs/2026-10-17-shipyard-design.md`

## Global Constraints

- Plugin name `shipyard`; repo `github.com/rafidzane/shipyard`, public; marketplace name `shipyard`; install with `/plugin marketplace add rafidzane/shipyard` then `/plugin install shipyard@shipyard`.
- Self-contained: no dependency on any other plugin.
- Nothing may require the `gh` CLI.
- Questions to the owner go through `AskUserQuestion`. Ask instead of guess, at every stage.
- No production code until `state.md` says `approved:`.
- One branch per run, `shipyard/<slug>`. Commit at the end of each stage. Locally, ask once (at approval) before pushing. Never merge to main.
- Fresh approval only when the plan gains or loses a goal, a screen or a database change. Smaller changes go in the final summary.
- `approval.md` uses only Markdown, fenced text wireframes and Mermaid, so the GitHub mobile app renders it.
- `approval.md` and `state.md` go in the project's change folder (`openspec/changes/<name>/`) when there is one, otherwise in `docs/shipyard/<slug>/`.
- Read-only agents (scout, reviewer) get no Write/Edit tools.
- `claude plugin validate --strict .` passes after every task.

## Review Focus

1. **The owner says "looks good, but change X" at the approval gate.** This must count as *not approved*: revise `approval.md`, then ask again. *(Eval case `partial-approval`, Task 3.)*
2. **A resumed run where `state.md` lacks `approved:` but code changes already exist.** The orchestrator stops and asks; it does not keep building. *(Eval case `resume-unapproved`, Task 3.)*
3. **A project with no `CLAUDE.md`, no `openspec/` and no test command.** It must fall back to `docs/shipyard/<slug>/` and ask how to run tests rather than inventing a command. *(Eval case `bare-project`, Task 3.)*
4. **A tiny request ("fix a typo in README").** The crew scales down: one builder, no parallel step, and approval is still required. *(Eval case `tiny-change`, Task 3.)*
5. **Bootstrap run outside the cloud, or run twice.** On a laptop it does nothing. A second run makes no changes and does not fail. *(Test in Task 4.)*

### Task 2: The crew (five agents)

**Files:**
- Create: `agents/scout.md`, `agents/planner.md`, `agents/builder.md`, `agents/tester.md`, `agents/reviewer.md`
- Test: `tests/check-agents.sh`

**Interfaces:**
- Produces, for Task 3. Each agent's frontmatter is `name`, `description`, `tools`, `model`, and each agent ends its work with a report in the stated shape:
  - `scout` (tools `Read, Grep, Glob, Bash`; model `haiku`). Reports:
    - `## Files` (path: why it matters)
    - `## Patterns to follow`
    - `## Project rules` (quoted from CLAUDE.md/AGENTS.md: process, test commands, versioning, test-data rules)
    - `## Unclear`: questions for the owner, each with why it matters
  - `planner` (tools `Read, Grep, Glob, Write, Edit`; model `sonnet`). Input: the request, the scout report, the owner's answers, the target folder. Writes `approval.md` from `skills/shipyard/approval-template.md`. Writes `proposal.md` and `tasks.md` only when the project has no process of its own. Reports the paths written, plus `## Unclear`.
  - `builder` (tools `Read, Grep, Glob, Write, Edit, Bash`; model `sonnet`). Input: the approved folder, its assigned task numbers and its owned file list.
    - Edits only owned files and ticks its tasks.
    - On anything unclear, or a need to touch an unowned file, it stops and reports `## Blocked` instead of guessing.
    - Reports `## Done` (tasks, files) and `## Blocked`.
  - `tester` (tools `Read, Grep, Glob, Write, Edit, Bash`; model `sonnet`). Writes tests for the acceptance criteria in `approval.md` and runs the project's test command(s) from the scout report. Reports `## Result` (pass/fail with the command and output tail) and `## Could not fix`.
  - `reviewer` (tools `Read, Grep, Glob, Bash`; model `sonnet`). Compares `git diff <base>...HEAD` to `approval.md` and the project rules. Reports `## Problems`, ranked `critical|warning`, each with file:line, and `## Scope changes`: anything that adds or drops a goal, a screen or a database change.
- All agents follow the project's rules as given in their prompt. Builder, tester and reviewer receive the run's folder path.

### Task 3: The orchestrator skill and its evals

**Files:**
- Create: `skills/shipyard/SKILL.md`, `skills/shipyard/approval-template.md`, `skills/shipyard/state-template.md`
- Test: `evals/<case>/prompt.md` + `evals/<case>/graders/*.md` for the cases below. Before writing them, check the exact case and grader format with `claude plugin eval --help` and the eval docs. Scaffold a tiny git repo per case where needed.

**Interfaces:**
- Consumes: the five agents' report shapes (Task 2).
- Produces:
  - **Slug:** the `/shipyard <request>` skill (`name: shipyard`, with a description that triggers on "/shipyard" or "build this with the crew") derives `<slug>`, a kebab-case slug of at most 5 words, from the request.
  - **`state-template.md`** fields, one per line:
    - `slug:`, `branch:`, `base:` (commit the branch started from), `folder:`
    - `stage:` (one of `research|questions|proposal|awaiting-approval|build|test|review|finish|done`)
    - `approved:` (empty, or `<date> — <one-line summary>`)
    - `push-ok:` (`yes|no|cloud`)
    - `open-questions:` (list), `scope-changes:` (list)
  - **`approval-template.md`** sections, in order:
    - `## What changes` (3–6 plain sentences)
    - `## Picture` (fenced text wireframe, or "No screen changes")
    - `## How it fits` (Mermaid flowchart of the parts touched)
    - `## Crew workflow` (Mermaid flowchart: which agent, which tasks, what runs in parallel)
    - `## Files` (path: change)
    - `## Acceptance criteria` (a checklist)
    - `## Risks`
    - `## Decisions made` (owner's answers and the planner's calls, labelled)

**SKILL.md decides these stages:**
1. **Research.**
   - Create or check out `shipyard/<slug>` from the current HEAD. If `state.md` already exists for the slug, resume from its `stage`, and first check its `approved:` against what has already been changed.
   - Dispatch `scout`.
2. **Questions.** Ask every `## Unclear` item, most important first, at most 4 per `AskUserQuestion` call. Repeat until nothing is unclear.
3. **Proposal.**
   - If the project has a process (the scout's `## Project rules`), run its propose step yourself; for OpenSpec that is `/opsx:propose <slug>` through the Skill tool, or the `openspec` CLI.
   - Then dispatch `planner` to add `approval.md`.
   - Write `state.md` and commit (`shipyard: proposal for <slug>`).
4. **Approval.**
   - Show the path to `approval.md`. Locally, if publishing an artifact is available, offer it as a page. Also ask `push-ok`, then push if yes, so the owner can read it on GitHub mobile.
   - Ask with `AskUserQuestion`: approve / change something.
   - Anything but a plain approve goes back to the planner.
   - On approve, set `approved:`, commit, and push if `push-ok`.
5. **Build.**
   - Hard check: `approved:` is set.
   - Split the tasks into areas with disjoint files. One area means one builder; otherwise dispatch builders in parallel in one message.
   - Answer `## Blocked` reports by asking the owner, then re-dispatch.
   - A scope change sets `approved:` empty and goes back to step 4.
   - Commit.
6. **Test.** Dispatch `tester`. On `## Could not fix`, send the failure to the owning builder once, then ask the owner. Commit.
7. **Review.** Dispatch `reviewer`. Send critical problems back to the builders (at most 2 rounds, then ask the owner); a scope change goes to step 4. Commit.
8. **Finish.**
   - Run the project's closing steps from the rules (for Leisuremint: `./scripts/bump-version.sh` once, tick `tasks.md`, `/opsx:archive`).
   - Check that no test data was left behind, as the project rules define it.
   - Commit and push (if `push-ok` or cloud).
   - Set `stage: done` and reply with: the branch, what was built, test results, smaller changes made after approval, and anything skipped and why.
- Cloud detection: environment variable `CLAUDE_CODE_REMOTE=true` means a cloud session, so `push-ok: cloud`.

### Task 4: Cloud bootstrap (spike, then keep or fall back)

- Create: `scripts/cloud-bootstrap.sh`, `tests/check-bootstrap.sh`
- Modify: `README.md` (the cloud section)

**Interfaces:**
- Produces: `scripts/cloud-bootstrap.sh`, for a project's `.claude/settings.json` `SessionStart` hook:
  - It exits 0 doing nothing unless `CLAUDE_CODE_REMOTE=true`.

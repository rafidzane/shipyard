# Plan 4: Learn (1.0.0)

> Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** close the loop. After a run, compare what was predicted with what happened, both during the run and after it shipped, and feed the result back into memory, so the next forecast, challenge and sizing in this project are better than the last. The owner can see whether Shipyard is getting better at their project.

**Architecture:** two moments, no scheduler. **At the finish**, the run scores its own predictions (`held`, `caught`, `missed`, from plan 2). **On the next run in the same project**, a short follow-up looks at what happened to earlier runs after merge: reverts, fixes that touched the same lines, bugs the owner reported, and scores those too. Results go into memory (plan 1) as incidents and patterns, and into a running scorecard.

**Depends on:** [Remember](2026-10-19-01-remember.md), [Predict](2026-10-19-02-predict.md), [Challenge](2026-10-19-03-challenge.md). **Overview:** [2026-10-19-intelligence-overview.md](2026-10-19-intelligence-overview.md)

## The scorecard

`docs/shipyard/memory/scorecard.md`, one row per finished run, appended:

```markdown
| Run | Date | Mode | Sized as | Actually | Predicted | Caught | Held | Missed in run | Missed after merge | Challenges that changed the plan |
|---|---|---|---|---|---|---|---|---|---|---|
| share-timeout-password-savings | 2026-10-18 | standard | 3 areas | 3 areas | 4 | 0 | 3 | 1 (R-x: idle 401 race) | 1 (fixed in idle-signout-message) | 1 of 2 |
```

At the top, three running numbers over the last 20 runs, recalculated at each finish:
- **Forecast hit rate:** problems that a row predicted ÷ all problems found (in the run and after merge). This is the number that should go up.
- **Sizing accuracy:** runs whose actual size matched the sizing's mode.
- **Challenge yield:** challenges that changed the plan ÷ challenges raised.

## Risks

- **Blaming the wrong run.** A later fix may touch the same lines for an unrelated reason. Guard: a miss after merge needs an overlapping diff and a fix/revert message, and the incident cites both commits so the owner can correct it.
- **Gaming the number** (fewer predictions to keep the hit rate up). Guard: the hit rate counts problems found, not predictions made, so predicting less lowers it.
- **The scorecard is meaningless for a while.** Guard: the numbers show only after 5 runs; before that, the summary says "not enough runs yet".
